## Image hosting (Cloudflare R2)
- All images and Atlas tiles are served from **Cloudflare R2** — account `484f994d4cda4a50fd47ae741cec8eb9` (`Nemocitizen@protonmail.com`'s account, a privacy alias the user controls on purpose), bucket `odyssey-assets`, public delivery via the `r2.dev` managed domain: `https://pub-b57180e24c9841f58854ecd1c164523a.r2.dev`. Migrated 2026-08-04 off Cloudinary (cloud `dhvvz91bh`) after that shared account was disabled for billing overage and permanently deleted — the account was shared across several unrelated local projects, and the overage was traced to this project's own bulk Atlas-tile upload (`747ffeb`/`da5c54b`, 5 days before the warning), not another project's traffic. `public/art/` is **git-ignored** (kept locally only as the upload master / for re-sync); it is NOT deployed. `public/hero.jpg` stays in the repo (LCP preload).
- **Object key scheme:** art masters at `art/<filename>.jpg` (mirrors `art.json`'s `file` field exactly, e.g. `file: "/art/achaeans-1.jpg"` → key `art/achaeans-1.jpg` → `assetUrl(a) = R2_BASE + a.file`); Atlas tiles at `atlas/<slug>/{z}/{row}/{col}.jpg` (see Atlas map section above); per-plate minimap thumbnails at `atlas/<slug>/thumb.jpg`.
- App delivers via `assetUrl(a)` in `App.tsx`: `${R2_BASE}${a.file}` — served as-is, no resize/format param. **R2 has no on-the-fly transform API** (unlike Cloudinary's `f_auto,q_auto,c_limit,w_N`), so there's no per-request AVIF/WebP negotiation or width capping anymore; this works because `public/art/` masters are already ImageMagick-recompressed to 1600px max / q82 / stripped at harvest time (see "Working with artwork" below), so serving the master directly is already close to optimal for both card covers and the lightbox. The `cld` field in `art.json` is now dead data (superseded by `file`-based URLs) — harmless, not worth a 574-entry cleanup pass.
- **Credentials:** `~/Documents/odyssey/.env.r2.local` (git-ignored via the `*.local` rule) — `CF_ACCOUNT_ID`, `CF_API_TOKEN` (Bearer token, account-wide `Workers R2 Storage: Edit`, used for bucket/domain admin calls), and `R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_S3_ENDPOINT` (S3-compatible credentials, used for bulk object upload — see gotcha below).
- **Uploading (`scripts/upload_to_r2.py`):** walks `public/art/*.jpg` and `plates/<slug>/tiles/**/*.jpg` for all 6 plates and pushes everything via **boto3 against R2's S3-compatible endpoint** (`endpoint_url=R2_S3_ENDPOINT`, `region_name="auto"`), 16 concurrent workers. Re-running is idempotent (plain overwrite) — no resume/skip logic, just re-upload everything.
- **Gotcha — the generic Cloudflare REST API (`api.cloudflare.com`, Bearer token) is NOT viable for bulk upload.** It works fine for one-off admin calls (bucket create, enabling the public managed domain) but has an aggressive **account-wide** rate limit (~1200 req/5min ≈ 4 req/s) shared across *all* Cloudflare API usage on the account, not anything R2-specific — a first attempt at uploading all ~11,650 objects through it stalled at ~36% behind constant 429s, even with backoff/retry across three different concurrency strategies. **R2's separate S3-compatible endpoint has no such limit** (it's real object-storage infrastructure, not the shared control-plane API) and completed the same full upload with 0 failures and no throttling. Rule of thumb: REST API for admin/config calls, S3-compatible endpoint for any bulk object PUT/DELETE loop.
- **Swap an image in place (no `art.json` change):** overwrite the same R2 key (`s3.upload_file(..., ExtraArgs={"ContentType": "image/jpeg"})` with `overwrite` implicit — R2 PUTs always overwrite). Unlike Cloudinary there's no automatic CDN purge/versioning, so a browser that already cached the old bytes at that URL may keep serving them for a while — if that matters (as it did for the Journey map's base image, previously handled via Cloudinary's `/v<version>/` path segment), consider a cache-busting query param or a new key + updated reference instead of an in-place overwrite.
- **Orphan cleanup after removals:** removing an image from `art.json` leaves its R2 object unused. No scripted cleanup exists yet (the Cloudinary-era orphan-sweep script was cloud-specific) — for now, cross-reference `art.json`'s `file`/`cld` values against a bucket listing (`s3.list_objects_v2`) by hand if this comes up. Low priority: storage is cheap and nothing currently prunes.
- Shell here is **zsh** (no `mapfile`/bash array slicing) — use Python for montages/scripts.
